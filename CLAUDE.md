# Kanban Task Board

WPF (.NET, `net10.0-windows`) desktop kanban app, SQLite-backed via `Microsoft.Data.Sqlite`. Personal project, developed from two computers with this folder synced via OneDrive and pushed to GitHub (`origin` = `JeremyHillier/kanban-program`).

## Working across two computers

- **Git via GitHub is the source of truth, not OneDrive.** OneDrive also raw-syncs the `.git` folder since the whole project sits inside OneDrive — that's a secondary convenience, not the sync mechanism. `git pull` at the start of a session. Don't leave uncommitted work sitting around between sessions on either machine.
- **Auto-push**: the user wants every commit pushed to GitHub immediately after it's made, without asking first — standing instruction, not a one-off. Push right after each commit on both machines.
- **Bump `<Version>` in `src\KanbanApp\KanbanApp.csproj` with almost every functional commit** — 45 of the last 53 commits did (patch bump for small fixes/tweaks, minor bump for feature additions, e.g. the original keyboard-shortcuts commit went 0.30.0 → 0.31.0). Easy to miss since nothing enforces it; check `git log -- KanbanApp.csproj` if unsure what the last bump looked like.
- If you ever see a stuck `index.lock`, weird "bad object", or other git corruption, it's almost certainly OneDrive's file-level sync colliding with git's own writes to `.git` (e.g. both machines touching it near-simultaneously). Recover via `git fsck` / re-clone from GitHub if needed; don't try to hand-fix `.git` internals.
- This file is the persistent shared brief between sessions/machines — Claude Code loads it automatically at the start of every session in this repo. Keep it updated with anything a fresh session on either computer would need to not re-derive from scratch. Session history and Claude's memory do **not** sync between machines — only files (including this one) do.
- Commit messages here are doing real work as a paper trail (e.g. `Fix the real cause of the quick-edit freeze` → `Fix the actual cause...`) — keep them descriptive; `git log` is the fastest way for a session on the other machine to re-orient.

## Build

`dotnet build` from the repository root builds `KanbanApp.slnx` (the app in `src\KanbanApp`, the tests in `tests\KanbanApp.Tests`). No special setup beyond the SDK.

## Tests

`dotnet test tests/KanbanApp.Tests` (xUnit, references the app project). Run it before committing. Tests never touch the real task file: they use `new DatabaseService(path)` against a `TempFolder`. Anything needing `MainViewModel` goes in `[Collection(WpfCollection.Name)]` and wraps its body in `wpf.Run(...)`, because the view model applies its theme through `Application.Current` and WPF objects are thread-bound. Internals are visible to the test assembly (`AssemblyInfo.cs`), so pure helpers can be `internal static` rather than public.

## Changelog

`CHANGELOG.md` is embedded in the exe and its last five versions are shown to users on the What's New screen. Write entries for customers: what changed for them, in plain words, as short bullets. Implementation detail belongs in the commit message, not here. Older entries from before this rule contain developer wording; they no longer appear in What's New.

Layout (from 0.116.5): `## <version> — <date>`, a blank line, the summary as `> - ` lines (one point per line, no wrapping or bold), a blank line, then optional detail as `- ` lines. What's New shows only the `> - ` lines (`ReleaseNotes.Parse`); a version without any (everything before 0.116.5) shows its `- ` lines instead. The download page's release notes take both, with the `> ` removed (the awk line under Publishing does this).

These bullets are also published as the release notes on the public download page, so write them website-ready: professional, complete sentences a customer or prospect could read cold. Lead with "New:", "Improved:" or "Fixed:" where it helps. No first person, no slang, no mention of tests, internals, the developer or how the change was requested - only what the product now does.

## Installers

`installer/build-installers.ps1` defaults to `-Channels Production` only, and that's the desired behavior now — the user no longer needs the Test channel installer built as a matter of course. Just run it with no `-Channels` arg. Only pass `-Channels Test` or `-Channels Production,Test` if the user explicitly asks for a Test build for some specific reason.

After building, say where the installer is and stop there. Never ask whether to install it on this PC, never offer to, and never run it: the user always installs it themselves. The only question to ask after a build is the publishing one below.

Code signing (Azure Artifact Signing) is wired in and switched off: `installer/Signing.ps1`, dot-sourced by the build script, signs only when `installer/signing.json` exists (account endpoint, account name, certificate profile; no secrets, the build PC's `az login` is the credential - safe to commit). Then every Production build signs the app exe after publish, passes `/DSigned=1` and an `azuresign` tool to ISCC so Inno signs the setup and uninstaller (`SignTool=azuresign`, `SignedUninstaller=yes` under `#ifdef Signed`), verifies with `signtool verify /pa`, and stops on any failure rather than produce an unsigned installer. Test builds are never signed. The user's setup steps are in their `Code Signing Setup.html` guide. To switch it on, write `installer/signing.json` from the three names the user sends (the JSON shape is in that guide, section 7), build, and check the output says "Signing: on".
**A running copy during Setup** (0.122.0): `PrepareToInstall` in the .iss (no `AppMutex` any more - Inno's own prompt only told the user to close the app themselves) finds the app by its mutex, asks the user, then sends the main window (found by title, `FindWindowByWindowName`) a registered window message `KanbanTaskBoard.CloseForSetup`. `MainWindow.SetupClose.cs` answers it: 2 = refused (`HasTaskWorkOpen`: an Add/Edit Task window, the Imported Tasks review, or Quick Add with text), else 1 and it closes itself normally (owned windows first, so backup and settings saves run). Setup loops with "finish the task, then OK" on a refusal, waits up to 20 s for the mutex to go, and falls back to "close it yourself". `CloseApplications=yes` stays as the Restart Manager fallback. WM_CLOSE was not used: a modal task window would swallow it. The harness in the scratchpad drove all three replies against a real window; the installer itself is never run here.

**What's New in Setup** (0.128.0): on an update, Setup shows a "What's New" page after Welcome listing every version newer than the one installed. The build renders `CHANGELOG.md` to `installer/Output/WhatsNew.txt` (`installer/render-whats-new.ps1`, run by `build-installers.ps1` before ISCC) using the same rule as `ReleaseNotes.Parse` - a version's `> - ` lines, or its `- ` lines when it has none - and the .iss carries it as a `dontcopy` file. `WhatsNewSince` in the .iss walks it newest first and **stops at the first version that is not newer** than the installed `DisplayVersion`: the 1.0.0-1.2.0 entries at the bottom of the changelog would otherwise count as newer than every 0.x version. A first install shows no such page. So keep the changelog newest-first.


## Publishing a release to the download page

Public download page: https://hillierconsulting.ca/kanban.html. It reads the latest release from the **public** repo `JeremyHillier/kanban-task-board-downloads` through the GitHub API, so publishing a release there is all it takes. The website itself never needs redeploying for a new version.

- **After every successful installer build, ask the user**: "Publish <version> to the download page?" Only publish on a yes. Never publish without asking.
- Prerequisite: the GitHub CLI. Check with `gh auth status`. If it is missing or not signed in, tell the user to run `winget install --id GitHub.cli` and then `gh auth login` (once per computer), and stop.
- Only Production channel installers are ever published, never the Test build.
- Tag is `v<Version>` from `src\KanbanApp\KanbanApp.csproj`. First check `gh release view v<Version> --repo JeremyHillier/kanban-task-board-downloads`. If that version is already released, ask before replacing its file (`gh release upload v<Version> "<installer>" --clobber --repo ...`); a real change should normally get a version bump instead.
- Release notes are that version's bullets from `CHANGELOG.md`, copied as written (customer wording, lines starting with `- `, which the page shows as a list), summary first. Write them to a temp file and pass `--notes-file`:
  `awk '/^## <Version> /{f=1;next} /^## /{if(f)exit} f && /^(> )?- /{sub(/^> /,""); sub(/\r$/,""); print}' CHANGELOG.md > <temp file>`
- Publish with:
  `gh release create v<Version> "installer/Output/Kanban Task Board-Setup-<Version>.exe" --repo JeremyHillier/kanban-task-board-downloads --title "Kanban Task Board <Version>" --notes-file <temp file> --latest`
- Never mark it `--prerelease` or `--draft` (the page only picks up the latest full release). Never push source code or anything other than the installer to that repo; the code repo `kanban-program` stays private.
- Afterwards confirm with `gh release view` and tell the user it is live at https://hillierconsulting.ca/kanban.html.

## Architecture

Standard MVVM:
- `Models/` — plain POCOs (`CardItem`, `Project`, `Goal`, `Flag`, `Person`, `SubTaskItem`, `CardAttachment`, `ArchivedCardInfo`/`DeletedCardInfo`, `ImportedTaskRow`, `ReportRow`).
- `ViewModels/` — `ObservableObject`/`RelayCommand` base, one VM per model, plus `MainViewModel` (large — settings passthrough, filters/sort, card CRUD, per-managed-list CRUD, lifecycle transitions).
- `Views/` — one Window per feature (XAML + code-behind). The main window's code-behind is one `partial class MainWindow` split by concern: `MainWindow.xaml.cs` (start-up, window size and position, status line, undo), `.Reminders.cs` (What's New, due reminders, time alerts), `.DragDrop.cs`, `.CardMenus.cs` (right-click menus), `.CardActions.cs` (quick edits, move/delete/done, add and edit dialogs, Waiting On prompts), `.Keyboard.cs`, `.Sidebar.cs` (filters, sorting, grips), `.Dialogs.cs` (the windows the buttons open), `.QuickAdd.cs`, `.Updates.cs`. Put a new handler in the file for its concern rather than back in `MainWindow.xaml.cs`. The task window (`AddTaskWindow`) is split the same way: `.xaml.cs` (constructors, change tracking and the unsaved-changes prompt, Waiting On, Save), `.Attachments.cs`, `.AttachmentMenu.cs`, `.SubTasks.cs`, `.Schedule.cs` (dates, due time, AM/PM, recurring), `.Lists.cs` (project, goal and flag choices), `.People.cs`, `.WhoTypeAhead.cs`, `.Templates.cs`. `TimelineWindow` has `.Screen.cs` and `.Print.cs`; `SettingsWindow` has `.TaskFile.cs` (moving and switching the task file, recent files, backups) and `.Folders.cs` (default folders, Your Details); `ReportBuilderWindow` has `.SavedViews.cs`, `.Dates.cs` and `.Statistics.cs`. Dashboard and Report/Print logic live mostly in Views' code-behind rather than dedicated ViewModels — an inconsistency with the rest of the app, not a bug.
- `Services/` — `DatabaseService` (SQLite, schema migration via ad hoc `MigrateColumn` calls, no formal migrations table; the links between tables are foreign keys, declared in `DatabaseService.ForeignKeys.cs` and enforced on every connection, with a one-time backed-up rebuild for older files - see Conventions, Database), `AppConfig` (bootstrap JSON: DB path, pending cleanup path), `AppChannel` (`#if TEST_CHANNEL` selects Production/Test data folder + mutex), `ReportService` (three partials: `ReportService.cs` picks, sorts and groups the rows; `.Preview` draws the FixedDocument for Preview/Print; `.Pdf` is the PDFsharp export, which reads Segoe UI straight from `%Windows%\Fonts` — fragile if that font isn't installed there; all word-wrapping, including the printed Timeline's, goes through `Services/TextWrap`), `ViewModels/PriorityList` (the task file's own priorities, highest first - see Priorities under Key conventions; never spell the names out), `ImportService` (ClosedXML Excel template + import).
- `Theming/ThemeManager.cs`, `Converters/`.

### Key conventions

- **Priorities are a list the user can change** (0.119.0; `ViewModels/PriorityList`, `MainViewModel.Priorities.cs`, `Views/ManagePrioritiesWindow`, `Models/PriorityColors`). A task still stores its priority as the *name* (`Cards.Priority`); the list - names in rank order, each with a colour key, and which one is the default - is one JSON value in the `PriorityList` setting (missing or unreadable = the standard High/Medium/Normal/Low with Normal the default). `MainViewModel.Priorities` is the one instance; every `CardViewModel` is handed it (`PriorityList = Priorities` in `AddCard` and `BuildCardViewModel`) and exposes `PriorityBrush` and `PriorityRank` - **sort by `PriorityRank`, colour by `PriorityBrush` / `Priorities.Brush(name)`, list by `Priorities.Names`, default by `Priorities.Default`; never write "High" or "Normal" in code**. A name not on the list (an older copy edited the file, an import) is kept, shown grey, sorted with the default, and offered in the task screen's box so saving doesn't change it; `Priorities.Resolve(text)` maps anything from outside to a list name or the default. Changes go through `AddPriority` / `RenamePriority` / `DeletePriority` / `MovePriority` / `SetPriorityColor` / `SetDefaultPriority`, which save and call `PrioritiesChanged` (filter options, every card's badge, filters, sort). A **rename** rewords every `Cards` row (board, archived, deleted - one SQL `UPDATE`), task templates, custom filters, saved report views and the board's selected filter; a **delete** moves tasks and templates to the default and drops the name from filters and views; both **clear the Undo history**, whose saved task copies still carry the old name. Like the other managed lists it is outside Undo and outside the Settings snapshot (the Settings button just opens the screen). Ways in: click the sidebar's Priority label, Settings, the + beside Priority on the task screen, and "Manage Priorities..." under Priority in the card and selection right-click menus. Quick Add takes `!` plus the start of a name that matches exactly one priority (`QuickAddParser.Parse(..., priorityNames)`); import templates list the names (`ImportService.SaveTemplate(..., priorities)`); `DashboardData.Build(..., priorities)` counts an unknown name with the default. `PriorityToBrushConverter`, `Models/Priorities` and `PriorityOptions` are gone.
- **Priority colours are a fixed, measured set** (`Models/PriorityColors`: key, badge colour, Dashboard light and dark). The first four are the original red/amber/grey/blue. The other four (Green, Purple, Pink, Teal) were chosen by search for the largest colour difference (CIELAB, under normal vision and simulated protan, deutan and tritan) from the fixed four and each other, within the app's muted range, readable under white text (badges) and clear of the chart card: closest pairs 14.7 (badges), 16.6 (light charts), 19.2 (dark charts). A first hand-picked teal and pink measured 2.9 - the same colour to some people. **Measure before changing or adding a colour**; this replaces judging by eye, as for the Dashboard colours below.
- **Column names and the move buttons' letters** (`Services/ColumnLetters`, `MainViewModel.Columns.cs`): a column's role is its internal `Name` ("To Do" ... "Done", never changed; code keys on it); the user only renames `DisplayName`. Each card's four move buttons bind their letter and tooltip to `MainViewModel.ToDoColumn` / `InProgressColumn` / `OnHoldColumn` / `WaitingColumn` (`QuickLetter`, `MoveToolTip`); Done's is always a tick. `ColumnLetters.Assign` gives the first letter of the first word that isn't a small joining word (so the standard names still give T, P, H, W), never repeats a letter (a clash takes another letter from the later column's name, then its position) and never gives X (the Delete button). `RefreshColumnLetters` runs in `Load` and after every rename. `UseColumnNames(StandardColumnNames | GtdColumnNames)` backs the two buttons in Settings; column names are in the Settings snapshot, so Cancel takes them back. Show a column to the user by `DisplayName` (`QuickAddColumnName` does for Quick Add).

- **Help text is short bullets** (`Views/HelpWindow.xaml`, 0.116.1): one idea per `BulletItem`, ideally one line at the window's width, under a section heading (`HelpSectionHeaderStyle`) and, for long topics, a grey sub-heading (`HelpSubHeaderStyle`). Never a paragraph; split a long point into two bullets. Keep the four `x:Name="HelpSection_..."` headers: the ? buttons in Add/Edit Task, Report Builder, Timeline and Settings scroll to them. When a feature changes, update its bullet in the same commit.

- **Messages go through `Services/Dialogs`, never `MessageBox.Show`** (0.116.0). `Dialogs.Tell(owner, title, text, tone, detail)` for a message, `Dialogs.Confirm(owner, DialogMessage.Ask(...))` / `AskDanger(...)` for a question, `Dialogs.Show` for three buttons (returns `DialogChoice`). `Views/MessageWindow` shows it in the app's theme. Layout rules, in `Services/DialogMessage.cs`: the first paragraph is the point, in bold (what happened, or the question); paragraphs split by a blank line; lines starting "• " are bullets; a path or an error from Windows goes in `Detail`, never in the text. Buttons are named for what they do ("Delete", "Replace It", "Restart Now"), never Yes/No. `AskDanger` makes the main button red and Enter choose the safe button; set `EnterChoosesMain = true` only when Undo covers it and it is asked many times a day (deleting a task). `Dialogs.Show` switches `ShutdownMode` to explicit while it is open, so a message before the main window exists does not end the app. `MessageWindowTests` fails if a new `MessageBox.Show(` appears anywhere but the crash prompt's fallback in `App.xaml.cs`. `DialogCopyright` skips `MessageWindow`.

- **Archived and Deleted Tasks windows** keep their own layouts (they differ on purpose: Deleted has an explanation line and the date inline; Archived has striped rows, a stamps line and double-click to reactivate) but share their logic in `Views/RecoverableTaskList.cs`: `RecoverableTaskList<T>` (full list, date-range filter - both ends count, an unreadable date is never hidden - and removal) and `RecoverableTaskPrompts` (the Permanently Delete menu and question). Note `ReactivateCard` reloads the board (`Load()` rebuilds `Columns`), so hold no column references across it.
- **Settings values**: on/off settings go through `DatabaseService.GetFlag(key, defaultValue)` / `SetFlag` (stored as "True"/"False"; a starts-on setting stays on unless it says "False", a starts-off one is on only for "True" - pinned by `SettingFlagTests`), whole numbers through `GetInt(key, defaultValue)`. Don't hand-write the strings again.
- **Adding a task field** (a new `Cards` column the user edits): add it to `EditableCardFields` in `DatabaseService.Cards.cs` (the record, `Columns()` and `CopyTo`) - AddCard's INSERT, UpdateCard's UPDATE and the task AddCard returns are all built from it. Then the `GetCards` reader, `MigrateColumn` in the schema (and raise the file format), `CardItem`/`CardViewModel`, `MainViewModel.AddCard`/`EditCard`/`PersistCard`, and `CardFieldsRoundTripTests`, which saves and reloads every field.
- **Managed lists** (Project/Goal/Person/Flag): each own table with `Id, Name, SortOrder, IsActive`. Soft-toggle via `SetXActive`; hard `DeleteX` only allowed from UI when nothing references it. Cards reference by FK (`ProjectId`/`GoalId`/`WhoId`/`CardFlags` join table). CRUD for all four is deduped through `ManagedList<TModel, TViewModel>` (`ViewModels/ManagedList.cs`) — each entity wires up its own DB delegates in `MainViewModel`'s constructor rather than repeating Add/Rename/Delete/SetActive logic per list. The four Manage screens are one window, `Views/ManageListWindow`, told which list by `Views/ManagedListKind` (title, wording, actions, and the email line for people only) - add a new managed list there rather than copying a window. All four share one model base (`Models/ManagedListEntry`), one set of database helpers for reading, adding, renaming and switching on/off (`DatabaseService.ManagedLists.cs`; each list's own file keeps only its delete, which differs, plus Flags' join table and People's email) and one view-model base (`ManagedListEntryViewModel<T>`).
- **Managed list names are unique, whatever their capitals** (`ManagedList.Add` / `Rename`; nothing in the database enforces it). `AddProject/AddPerson/AddGoal/AddFlag` return a `ManagedAddResult` (the item, plus `Added` / `AlreadyThere` / `SwitchedBackOn` - an inactive match is made active again rather than duplicated); `RenameX` returns false when another entry has the name. UI callers show the wording through `ManagedListPrompts` and use `result.Item` rather than looking the name up again. Task files from before 0.109.0 can already hold a pair (a customer's crash log showed one: the second `AddPerson` went through, then `SyncFilterOptions` threw on the repeated name) - `SyncFilterOptions` now de-duplicates, so such files work and the spare can be deleted from its Manage screen.
- **Walking up from an event's `OriginalSource`**: text inside a `TextBlock` is a `Run`, which is not a `Visual`, and `VisualTreeHelper.GetParent` throws on it (a second crash from the same log: double-clicking text in the Reminders list). Use `current is Visual ? VisualTreeHelper.GetParent(current) : LogicalTreeHelper.GetParent(current)`.
- **Type-ahead in the Who picker** (`AddTaskWindow.WhoTypeAhead.cs`, `TypeAheadMatcher` - unit-tested): the picker is tickboxes in a Popup, so it gets no stock text search. Typing on the button or in the list focuses the first name starting that way (then surnames); letters within a second build on each other; Space always ticks the focused person (handled in `Who_PreviewKeyDown` by flipping `IsChecked`, not left to the CheckBox, whose own Space handling takes and releases mouse capture and closed the `StaysOpen="False"` popup in testing), so a name with a space in it is reached by its first name or surname alone; Enter/Esc close the list instead of reaching the window's Save/Cancel. `RebuildWhoItems` puts the focus back on the same person, because ticking rebuilds the rows. The board's multi-select filter lists use stock `TextSearch.TextPath="Name"`.
- **Compact cards** hide the large-only detail panel; the Waiting On line is the one detail repeated outside it (a second `TextBlock` shown only when `IsWaiting` and not `IsLargeCards`), by the user's choice. Keep the two in step.
- **Task soft-delete/archive**: `Cards.IsArchived` and `Cards.IsDeleted` are independent flags. Every lifecycle transition writes to `CardHistory`, which also backs the archived/deleted list's "when" display via `MAX(Timestamp)` — there's no dedicated timestamp column for that.
- **Settings**: in-app preferences live in the SQLite `Settings` key/value table (`GetSetting`/`SetSetting`), read once into `MainViewModel` at `Load()`. `AppConfig`'s JSON file is only for bootstrap info needed before the DB is even open.
- **`Who` legacy column**: `Cards.Who` (free text) still exists alongside `WhoId` (FK to `People`), kept only for the one-time `BackfillPeopleFromLegacyWho` migration. Don't write to `Who` in new code.
- **Recurrence**: `SpawnNextOccurrence` creates the next task when a recurring one completes — check this if adding new completion-adjacent behavior. `Cards.RecurrencesLeft` (0.111.0, file format 3) is how many times the task still happens counting itself; null means no end. Each spawn passes one fewer and 1 is the last. Whether to spawn is `CardViewModel.HasNextOccurrence` - use it rather than re-spelling the IsRecurring/pattern/NextOccurrenceSpawned test (the delete prompts use it too). Turning Recurring off clears the count (`AddCard`/`EditCard` store it only when recurring). Templates carry it as `RecurrenceCount`.
- **Completion time**: `Cards.CompletedAt` is set whenever a card enters the Done column (`DatabaseService.MoveCard`, or `AddCard` straight into Done) and cleared when it leaves (`MoveCard` to any other column, `ReactivateCard`). `UpdateCard` never touches it, so edits don't move it. Archiving keeps the card's Done column, so archived cards keep theirs. Anything that puts a card into or out of Done by another route must maintain it too. Pre-existing Done/archived cards are backfilled at startup from `CardHistory` ("Moved ... to Done" / "Added to Done"), then the archive time, then `LastUpdated`.
- **Email This Task** (`OutlookEmailHelper`): each compose that gets as far as a window (or the clipboard) is recorded by `MainViewModel.RecordCardEmailed(card, recipients, how)` as an `Emailed` row in `CardHistory` ("to sam@x.com, in Outlook" / "in your email app" / "copied to the clipboard"); `GetEmailHistory` reads them newest first and the task screen shows `EmailStampText` under Last updated with `EmailHistoryText` as its tooltip (0.123.0). It records the email being opened, never sent - the app cannot know. classic Outlook is driven by late-bound COM and gets attachments plus the user's signature. If COM can't open a compose window (the new Outlook has no COM, or no Outlook is installed), it falls back to a `mailto:` link in the default mail app (capped at `MaxMailtoLength`) and opens a temp folder with the task's import `.xlsx` and attachment copies to drag in. Only fall back before the Outlook window is showing, otherwise the user gets two emails.
- **Emailing several tasks** (0.133.0; `OutlookEmailHelper.Group.cs`): `ComposeTasksEmail(owner, cards, viewModel)` - one email for a selection (selection menu, "Email These N Tasks") or a project's open tasks (card menu, "Email All <Project> Tasks (N)", `MainViewModel.OpenTasksInProject`: board tasks of that project outside Done, in board order). To = every address on the tasks once (`GroupRecipients`, may be empty); subject "Tasks: <Project> (N)" or "Tasks (N)"; the body is a table (title, column, due, priority, people, waiting on) and **one** Excel file of every task (`ImportService.SaveTasksFile`, which `SaveSingleTaskFile` now wraps), each with its Task ID via `BuildImportRow`, so a group sent back updates the same tasks. The tasks' own attachments are deliberately left out (size); the email says so. Same Outlook-then-mailto route as one task. Each task gets an Emailed history row with "with N other tasks" (`RecordCardEmailed(..., groupSize)`).
- **Schedule in Outlook** (0.131.0; `Services/OutlookCalendarHelper`, `Services/CalendarFile` - pure, unit-tested in `CalendarFileTests`): an appointment for a task, built like Email This Task. Classic Outlook through late-bound COM (`CreateItem(1)`, olAppointmentItem; subject, times, body from `OutlookEmailHelper.AppendPlainTextDetails`, the task's attachments, then `Display` - never saved for the user); if Outlook can't make one, an `.ics` file (`CalendarFile.BuildIcs`: floating local times, RFC 5545 escaping, 75-byte folding that never splits a character) is written to `%TEMP%Kanban Task Board Calendar` and opened in whatever handles calendar files (the new Outlook, Windows Calendar). When it goes (`CalendarFile.For`): at the due time for 30 minutes; all day (free, not busy) on a due date with no time; otherwise the next half hour. Each time is a `Scheduled` row in `CardHistory` (`RecordCardScheduled`, details "for Oct 12, 2026 at 2:30 PM, in Outlook"); the task screen shows `ScheduleStampText` under the emailed line. Ways in: the card menu, a calendar quick button on **large cards only** (beside the flag; compact cards don't get it, to keep their height), and the task screen's Schedule button (edit mode), which uses the **on-screen** title, due date and time, unsaved or not.
- **Dropping on Import Tasks** (0.120.0; `Services/ImportDrop`, `OutlookDragDropHelper.Msg.cs`, `ImportTasksWindow`): the whole window takes a drop (`AllowDrop` on the Window, so dropping on a button works too; the dashed `DropZone` only shows where to aim and lights up via the window's `IsDragOver` dependency property - keep its colours in the Style, a local `BorderBrush` on the Border beat the trigger). Dropped items go through `OutlookDragDropHelper.ExtractDroppedFiles` into a per-window temp folder (deleted on close), then `ImportDrop.FindExcelFiles`: .xlsx as is, a .msg has its Excel attachments pulled out by `ExtractMsgAttachments` (reads the compound file's `__attach_version1.0_#N` storages and MAPI properties 3707/3704 name, 3701 bytes - no Outlook needed), anything else is named as left out. Both the drop and Choose File then go through `ImportFiles`: read every file, `ImportDrop.DescribeForConfirm` lists the tasks for a yes, import, open the review screen (the old "Import Complete" message is gone). `WriteMsgWithAttachments` builds a minimal .msg for the tests, which round-trip a real single-task file through one.
- **Website links are restricted**: `UrlLauncher.TryNormalize` only lets http/https (with a dotted host or `localhost`, no user-info) and `mailto:` through; bare `name@x.y` becomes `mailto:`, a bare host gets `https://`. `UrlLauncher.Open` refuses anything else at launch time (a task file can come from someone else), and Add/Edit Task refuses to save it. - **Panel colours**: theme brushes set in `ThemeManager.Apply` (defaults in `App.xaml`). `AccentPanelBrush`/`AccentPanelBorderBrush` are the header bar: mid-blue in light, deep navy in dark, and **white text sits directly on it, so keep it at 4.5:1 or better against white**. `SidebarPanelBrush`/`SidebarPanelBorderBrush` are the button column: pale blue in light mode (the user found a mid-navy washed the slate and blue buttons out), deep navy in dark. Nothing in the button column is drawn straight onto that background except separators and the resize grips (`SidebarGripBrush`) - every label and button is its own coloured box with white text - so a new element placed directly on it needs a colour that works on both the pale and the navy.
- **The banner's filter line** (0.125.0; `Services/FilterSummary`, `MainViewModel.CustomFilters.cs`, the header in `MainWindow.xaml`): `FilterSummaryText` / `HasFilterSummary` / `FilterSummaryToolTip` describe what is narrowing the board - `FilterSummary.Parts(CurrentFilterState(), HideFutureTasks)` names every filter in button-column order (day buttons, range, lists, goal, flag, waiting, keyword, Hide Future), `Line` adds a saved custom filter's name and Alt key when `FilterSummary.Same` matches a slot, and the count showing. **A new kind of filter must be added to `CustomFilter`/`CurrentFilterState` and to `FilterSummary.Parts`**, or the banner will not mention it. Refreshed through `NotifyFilterSummaryChanged`, which `NotifyHiddenTasksChanged` (end of `ApplyFilters`, `RefreshDashboardStats`) and the custom-filter save/rename/clear call. In the header it is a translucent pill under the title whose row is always reserved (`Visibility=Hidden`, never Collapsed, and the title gives up its empty descender space with negative margins) so the banner's height - and the board under it - never moves as filters go on and off; `HeaderGrid_SizeChanged` caps the pill's width at the gap between the counts and their mirror image, past which it trims and the tooltip has it all.
- **Collapsible button column** (`MainViewModel.Sidebar.cs`): `IsSidebarCollapsed` swaps the 344-wide column for a 30-wide strip docked on the same side (both are in `MainWindow.xaml`, one always collapsed). Toggled by the Hide link, a click on the strip, or Alt+B; remembered in the `SidebarCollapsed` setting. It is a view choice like Hide Future, so it is **not** in the Settings snapshot. Because the filters are out of sight while collapsed, the strip shows `HiddenTasksLabel` ("3 hidden by filters"): `HiddenTaskCount` is simply every card with `IsVisible` false, whatever hid it, and is refreshed at the end of `ApplyFilters` and in `RefreshDashboardStats`. The arrows and the Hide link's side follow `IsButtonsOnRight`. **Anything new placed only in the button column needs a keyboard shortcut or another way in**, since the column may be hidden.
- **Compact buttons** (second half of `MainViewModel.Sidebar.cs`; Settings, so it **is** in the Settings snapshot): a tighter button column, 300 wide instead of 344 and about 140 shorter. **Tighter, not smaller text** - some labels are 9 px already, so plain scaling was rejected. What changes, all through `IsCompactButtons`: `SmallSquareButtonStyle` gets lower (36 high, same 48 width because the labels need it); the large lower buttons use `LargeSquareButtonStyle` and drop from 72x72 to 60x38 (still four to a row, two-word labels still fit on two lines); padding 12 -> 8; and From/To switch from side by side to stacked (`DateRangeColumns` on a `UniformGrid`), because at 300 wide two full dates in one row were cut off at "12/28/20" - their labels widen to line up with Goal/Flag/Keyword. The parked-ideas entry for this is now done.
- **Quick Report and relative report dates** (`Services/ReportRunner.cs`, `Services/RelativeDate.cs`, `QuickReportWindow`): `ReportRunner` runs a `SavedReportView` straight from its stored fields (rows, FixedDocument, PDF, and the parameter summary), so a report can be made without the Report Builder screen; the Report Builder still builds from its own controls, and the two agree because both call `ReportService.BuildRows`. A saved view's `DueFrom`/`DueTo`/`ArchivedFrom`/`ArchivedTo` can be a fixed `yyyy-MM-dd` or a relative `today`, `today+7`, `today-30` (`RelativeDate.Resolve(saved, today)`, resolved on the day the report runs). In the Report Builder a picker shows the real day and carries the relative text in its `Tag` for as long as it still shows that day (`SetDate`/`SavedDate`): re-saving a loaded view keeps it relative, picking a day by hand makes it fixed. The Today buttons save `today`; right-click offers `today±N`. `DateKindText` under the pickers says which kind each date is (`RefreshDateKind`, on every change), because the pickers themselves always show a real day and the user could not tell the two apart. `SetDate` is an instance method for that reason. Quick Report is `Ctrl+Shift+P` and the green button on the Archive row; it remembers `QuickReportLastView`.

The header's top right holds only the TEST BUILD badge.
- **Remembering where a window was** (`Views/WindowPlacementMemory.cs`): `WindowPlacementMemory.Attach(window, viewModel, key)` in a window's constructor restores its last size, position and maximized state (`MainViewModel.WindowPlacement(key)` / `SaveWindowPlacement`, setting `<key>WindowPlacement` = "left,top,width,height,maximized") and saves them on `Closing`. The size is capped at the work area and the position is only used when it overlaps a monitor that is there now (`IsOnAScreen`, the board window's test) - otherwise the window opens where its `WindowStartupLocation` says. The Dashboard uses it (key `Dashboard`). The Timeline keeps its older size-only setting on purpose (always centred); the board window has its own four settings. Use `Attach` for any further window that should remember its place.

- **Task templates** (`Models/TaskTemplate.cs`, `DatabaseService.Templates.cs`, `MainViewModel.Templates.cs`, `AddTaskWindow.Templates.cs`, `ManageTemplatesWindow`): a `TaskTemplates` table holding `Id`, `Name` and the rest as one JSON value, so adding a task field to templates needs no schema change - add it to `TaskTemplate`, `TemplateFromCard`, `AddTaskWindow.BuildTemplateFromForm` and `ApplyTemplate`. Deliberately not kept: column, attachments, Waiting On, sub-task ticks, and absolute dates (`DueInDays` / `StartInDays` are days from the day the template is used; past dates become null). References are by id, and one that no longer exists or is inactive is simply left unset when applied. Saving under an existing name (any capitalisation) replaces it, after a confirm in `TemplatePrompts.SaveAs`. The Template row shows on every *new* task (greyed, with a how-to hint, while there are no templates) and never when editing. Other ways in: right-click the New Task button (`NewTaskButton_PreviewMouseRightButtonUp` - start from a template via `AddTaskWindow.StartFromTemplate`, or Manage Templates) and Alt+M for Manage Templates.
- **Quick Add** (`MainWindow.QuickAdd.cs`, `QuickAddWindow`, `MainViewModel.QuickAdd.cs`, `Services/QuickAddParser.cs` - the parser is pure and unit-tested): `RegisterHotKey` on the main window's handle (Ctrl+Alt+N; the Test build adds Shift so both can run together), delivered as `WM_HOTKEY` to a hook added in `OnSourceInitialized`. It only works while the app runs. If Windows refuses the key, `MainViewModel.QuickAddHotkeyProblem` is set and Settings shows it. One Quick Add window at a time; it is topmost, does not close on losing focus, and stays open after each add. `QuickAddHotkeyEnabled` is a Settings preference, so it is in `SettingsSnapshot`. Parser rule: a code is only a code when the whole word matches (`!high`, `@start-of-one-person's-name`, `/tomorrow` `/fri` `/+3` `/10-15` `/2026-10-15`); anything else stays in the title untouched. `MainWindow.ShowStatusMessage` is the shared "line at the foot of the board" used by Undo and Quick Add.
- **Testing windows outside the app**: to render real windows from a scratch exe, reference `srcKanbanAppKanbanApp.csproj`, set `Application._resourceAssembly` (private static, via reflection) to the KanbanApp assembly, create a plain `new Application()`, and give it App.xaml's resources by `XamlReader.Parse`-ing the inside of `<Application.Resources>` wrapped in a `<ResourceDictionary>`. Then drive everything from `Dispatcher.CurrentDispatcher.BeginInvoke(...)` + `Dispatcher.Run()`. Never construct `KanbanApp.App` in a harness: its constructor queues `OnStartup`, which runs as soon as the dispatcher does (even without `app.Run()`) and opens the splash, the channel's real task file (Test data for Debug builds) and a second main window. Subclassing `App` to skip it fails (`LoadComponent` rejects the type). Hand-pushed `DispatcherFrame` + `DispatcherTimer` pumps can wedge after a few windows open and close (seen while testing the snooze menu), even though the app itself is fine. For multi-window UI checks, drive the steps from inside a real `Application.Run()` loop with `await Task.Delay(...)`.

## Known rough edges

- Report / Print bypass MVVM (logic in code-behind) — inconsistent with the rest of the app, not urgent to fix but don't copy the pattern forward. The Dashboard no longer does: its numbers are `Services/DashboardData.cs` (unit-tested in `DashboardDataTests`), its drawing `Views/DashboardCharts.cs`.
- **Dashboard colours** (`DashboardPalette` in `Views/DashboardCharts.cs`) were checked with a palette validator (colour-blind separation of neighbouring colours, contrast against the chart card) separately for light and dark - dark is its own set of steps, chosen by `MainViewModel.IsDarkMode`, not a flip. On Hold is magenta, not the board's orange: orange beside In Progress yellow failed the check. Re-check any colour change the same way rather than by eye. ## Conventions

How the program is laid out and built (recorded 2026-09-27). Before adding a convention, screen,
service or document, check this section and keep to it.

- **Layout:** `KanbanApp.slnx` at the root; the app in `src\KanbanApp`; tests in `tests\KanbanApp.Tests`;
  `installer\` with `build-installers.ps1`, the `.iss` and `Signing.ps1`; `CHANGELOG.md`, `CLAUDE.md`,
  `README.md` at the root. .NET 10, `Nullable` and `ImplicitUsings` on, no `LangVersion`. `.editorconfig`
  and `.gitattributes` set UTF-8 without BOM, CRLF, 4 spaces, no trailing whitespace.
- **Code style:** file-scoped namespaces that follow the folder; one type per file, partial classes split
  by concern with a `.Concern.cs` suffix; Allman braces; `_camelCase` private fields; primary constructors
  where they read well. Comments explain why; `//` comments throughout, `///` summaries where they help.
- **View models:** `ObservableObject` (`OnPropertyChanged`, `SetField`) and `RelayCommand` (the
  `Action<object?>` and `Action` constructors, `CanExecuteChanged` on `CommandManager.RequerySuggested`),
  one file each, in `ViewModels`.
- **App info and channel:** `Services/AppInfo` (`ProductName`, `Company`, `Website`, `DownloadPageUrl`,
  `SupportEmail` support@hillierconsulting.ca, `InfoEmail` info@hillierconsulting.ca, `Copyright` with
  the year from the clock). `Services/AppChannel` picks Test or Production at build time
  (`-p:AppChannel=Production`; plain builds are Test) with its own `%LocalAppData%\KanbanApp[.Test]\config.json`
  and data folder, and a " (Test)" suffix on screen.
- **Startup:** one mutex `KanbanTaskBoard-<Channel>`; `ShutdownMode.OnExplicitShutdown` until the board is
  showing, then `OnMainWindowClose`; a backup before the task file's structure is changed; the main
  window; What's New once per version; the update check after the window is up.
- **Messages:** never `MessageBox.Show`. `DialogMessage` (the first paragraph is the point, in bold;
  "• " bullets; a path or an error in `Detail`; buttons named for what they do, never Yes/No) shown by
  `Dialogs` in `MessageWindow`. `AskDanger` makes the main button red and Enter choose the safe one. A
  test fails if `MessageBox.Show(` returns.
- **Window buttons never leave the screen** (0.120.1; a standing rule across the user's apps, not just
  this one). Every window is laid out as a Grid of two rows: the content in a `ScrollViewer` in a `*`
  row, and the buttons (Close, Cancel, Save, OK, the default and cancel buttons) in an `Auto` row
  beneath it, so a small screen or a large font scrolls the content and never the buttons. A
  DockPanel with the buttons docked Bottom and the ScrollViewer last is the same thing. Never put
  the buttons inside the ScrollViewer, and never rely on a fixed `Height` fitting. `Theming/WindowFit`
  is the safety net: a class handler on `Window.Loaded` caps every window's `MaxHeight`/`MaxWidth` at
  the work area of the monitor it is on (WPF units, DPI-aware) and moves a window that hangs past the
  edge back in - which is exactly why the content must scroll, or it gets clipped instead.
  `WindowLayoutTests` reads every window's XAML and fails on an action button inside a
  `ScrollViewer`; `WindowFitTests` shows real windows against the work area.
- **Main screen foot:** "Version x.y.z[ (Test)]", an About link, "© <year> Jeremy Hillier Consulting Inc".
  About shows the version, channel, file paths, both email addresses and the website. Every other dialog
  carries the copyright line bottom-right, stamped by a class handler on `Window.Loaded`
  (`Theming/DialogCopyright`).
- **Help:** short bullets under headings, one idea per bullet, never a paragraph; the ? buttons land on
  their topic.
- **Changelog:** newest first; `## <version> — <date>`; the summary as `> - ` lines (one point per line,
  no wrapping or bold, starting "New:", "Improved:" or "Fixed:" where it helps), then optional `- `
  detail. What's New shows the `> - ` lines only. Bump `<Version>` in the app csproj with every change;
  a pure refactor ships as a "Maintenance release" line.
- **Database:** SQLite through Microsoft.Data.Sqlite; dates as `yyyy-MM-dd` text, timestamps as
  `yyyy-MM-dd HH:mm:ss`, bools as 0/1 in tables; the `FileFormat` setting stamps the newest format that
  has ever saved the file, only ever goes up, and brings a warning before a file a newer version has used
  is opened. Migrations are additive (`MigrateColumn`), with one exception: the links between tables are
  foreign keys (`DatabaseService.ForeignKeys.cs` holds the linked tables' definitions), enforced on every
  connection (`Foreign Keys=True`; the SQLite build in use has them on by default, so the upgrade
  connection says `False` explicitly), and a file from before they were declared is rebuilt once - backed
  up first, stray references tidied, checked with `PRAGMA foreign_key_check`, or left exactly as it was
  with the reason in `ForeignKeyUpgradeProblem`. Backups go through `SqliteConnection.BackupDatabase`
  into `Backups` beside the task file, newest N retained; `before-update` copies are never pruned.
  Microsoft.Data.Sqlite's default 30-second busy timeout applies everywhere. Never rewrite real data files
  to rename tables or change storage formats.
- **Installer:** Inno Setup, `{userpf}\Kanban Task Board`, `PrivilegesRequired=lowest`, one AppId per
  channel, the EULA as `LicenseFile`, signing through `Signing.ps1` once `installer\signing.json` exists;
  only Production installers are ever published.
