# Kanban Task Board

WPF (.NET, `net10.0-windows`) desktop kanban app, SQLite-backed via `Microsoft.Data.Sqlite`. Personal project, developed from two computers with this folder synced via OneDrive and pushed to GitHub (`origin` = `JeremyHillier/kanban-program`).

## Working across two computers

- **Git via GitHub is the source of truth, not OneDrive.** OneDrive also raw-syncs the `.git` folder since the whole project sits inside OneDrive — that's a secondary convenience, not the sync mechanism. `git pull` at the start of a session. Don't leave uncommitted work sitting around between sessions on either machine.
- **Auto-push**: the user wants every commit pushed to GitHub immediately after it's made, without asking first — standing instruction, not a one-off. Push right after each commit on both machines.
- **Bump `<Version>` in `KanbanApp.csproj` with almost every functional commit** — 45 of the last 53 commits did (patch bump for small fixes/tweaks, minor bump for feature additions, e.g. the original keyboard-shortcuts commit went 0.30.0 → 0.31.0). Easy to miss since nothing enforces it; check `git log -- KanbanApp.csproj` if unsure what the last bump looked like.
- If you ever see a stuck `index.lock`, weird "bad object", or other git corruption, it's almost certainly OneDrive's file-level sync colliding with git's own writes to `.git` (e.g. both machines touching it near-simultaneously). Recover via `git fsck` / re-clone from GitHub if needed; don't try to hand-fix `.git` internals.
- This file is the persistent shared brief between sessions/machines — Claude Code loads it automatically at the start of every session in this repo. Keep it updated with anything a fresh session on either computer would need to not re-derive from scratch. Session history and Claude's memory do **not** sync between machines — only files (including this one) do.
- Commit messages here are doing real work as a paper trail (e.g. `Fix the real cause of the quick-edit freeze` → `Fix the actual cause...`) — keep them descriptive; `git log` is the fastest way for a session on the other machine to re-orient.

## Build

`dotnet build` from the project root. No special setup beyond the SDK.

## Tests

`dotnet test tests/KanbanApp.Tests` (xUnit, references the app project; `KanbanApp.csproj` excludes `tests\**` from its own globs). Run it before committing. Tests never touch the real task file: they use `new DatabaseService(path)` against a `TempFolder`. Anything needing `MainViewModel` goes in `[Collection(WpfCollection.Name)]` and wraps its body in `wpf.Run(...)`, because the view model applies its theme through `Application.Current` and WPF objects are thread-bound. Internals are visible to the test assembly (`AssemblyInfo.cs`), so pure helpers can be `internal static` rather than public.

## Changelog

`CHANGELOG.md` is embedded in the exe and its last five versions are shown to users on the What's New screen. Write entries for customers: what changed for them, in plain words, as short bullets. Implementation detail belongs in the commit message, not here. Older entries from before this rule contain developer wording; they no longer appear in What's New.

These bullets are also published as the release notes on the public download page, so write them website-ready: professional, complete sentences a customer or prospect could read cold. Lead with "New:", "Improved:" or "Fixed:" where it helps. No first person, no slang, no mention of tests, internals, the developer or how the change was requested - only what the product now does.

## Architecture

Standard MVVM:
- `Models/` — plain POCOs (`CardItem`, `Project`, `Goal`, `Flag`, `Person`, `SubTaskItem`, `CardAttachment`, `ArchivedCardInfo`/`DeletedCardInfo`, `ImportedTaskRow`, `ReportRow`).
- `ViewModels/` — `ObservableObject`/`RelayCommand` base, one VM per model, plus `MainViewModel` (large — settings passthrough, filters/sort, card CRUD, per-managed-list CRUD, lifecycle transitions).
- `Views/` — one Window per feature (XAML + code-behind). The main window's code-behind is one `partial class MainWindow` split by concern: `MainWindow.xaml.cs` (start-up, window size and position, status line, undo), `.Reminders.cs` (What's New, due reminders, time alerts), `.DragDrop.cs`, `.CardMenus.cs` (right-click menus), `.CardActions.cs` (quick edits, move/delete/done, add and edit dialogs, Waiting On prompts), `.Keyboard.cs`, `.Sidebar.cs` (filters, sorting, grips), `.Dialogs.cs` (the windows the buttons open), `.QuickAdd.cs`, `.Updates.cs`. Put a new handler in the file for its concern rather than back in `MainWindow.xaml.cs`. The task window (`AddTaskWindow`) is split the same way: `.xaml.cs` (constructors, change tracking and the unsaved-changes prompt, Waiting On, Save), `.Attachments.cs`, `.AttachmentMenu.cs`, `.SubTasks.cs`, `.Schedule.cs` (dates, due time, AM/PM, recurring), `.Lists.cs` (project, goal and flag choices), `.People.cs`, `.WhoTypeAhead.cs`, `.Templates.cs`. Dashboard and Report/Print logic live mostly in Views' code-behind rather than dedicated ViewModels — an inconsistency with the rest of the app, not a bug.
- `Services/` — `DatabaseService` (SQLite, schema migration via ad hoc `MigrateColumn` calls, no formal migrations table), `AppConfig` (bootstrap JSON: DB path, pending cleanup path), `AppChannel` (`#if TEST_CHANNEL` selects Production/Test data folder + mutex), `ReportService` (PDFsharp export, reads Segoe UI straight from `%Windows%\Fonts` — fragile if that font isn't installed there), `ImportService` (ClosedXML Excel template + import).
- `Theming/ThemeManager.cs`, `Converters/`.

### Key conventions

- **Managed lists** (Project/Goal/Person/Flag): each own table with `Id, Name, SortOrder, IsActive`. Soft-toggle via `SetXActive`; hard `DeleteX` only allowed from UI when nothing references it. Cards reference by FK (`ProjectId`/`GoalId`/`WhoId`/`CardFlags` join table). CRUD for all four is deduped through `ManagedList<TModel, TViewModel>` (`ViewModels/ManagedList.cs`) — each entity wires up its own DB delegates in `MainViewModel`'s constructor rather than repeating Add/Rename/Delete/SetActive logic per list.
- **Managed list names are unique, whatever their capitals** (`ManagedList.Add` / `Rename`; nothing in the database enforces it). `AddProject/AddPerson/AddGoal/AddFlag` return a `ManagedAddResult` (the item, plus `Added` / `AlreadyThere` / `SwitchedBackOn` - an inactive match is made active again rather than duplicated); `RenameX` returns false when another entry has the name. UI callers show the wording through `ManagedListPrompts` and use `result.Item` rather than looking the name up again. Task files from before 0.109.0 can already hold a pair (a customer's crash log showed one: the second `AddPerson` went through, then `SyncFilterOptions` threw on the repeated name) - `SyncFilterOptions` now de-duplicates, so such files work and the spare can be deleted from its Manage screen.
- **Walking up from an event's `OriginalSource`**: text inside a `TextBlock` is a `Run`, which is not a `Visual`, and `VisualTreeHelper.GetParent` throws on it (a second crash from the same log: double-clicking text in the Reminders list). Use `current is Visual ? VisualTreeHelper.GetParent(current) : LogicalTreeHelper.GetParent(current)`.
- **Type-ahead in the Who picker** (`AddTaskWindow.WhoTypeAhead.cs`, `TypeAheadMatcher` - unit-tested): the picker is tickboxes in a Popup, so it gets no stock text search. Typing on the button or in the list focuses the first name starting that way (then surnames); letters within a second build on each other; Space always ticks the focused person (handled in `Who_PreviewKeyDown` by flipping `IsChecked`, not left to the CheckBox, whose own Space handling takes and releases mouse capture and closed the `StaysOpen="False"` popup in testing), so a name with a space in it is reached by its first name or surname alone; Enter/Esc close the list instead of reaching the window's Save/Cancel. `RebuildWhoItems` puts the focus back on the same person, because ticking rebuilds the rows. The board's multi-select filter lists use stock `TextSearch.TextPath="Name"`.
- **Compact cards** hide the large-only detail panel; the Waiting On line is the one detail repeated outside it (a second `TextBlock` shown only when `IsWaiting` and not `IsLargeCards`), by the user's choice. Keep the two in step.
- **Task soft-delete/archive**: `Cards.IsArchived` and `Cards.IsDeleted` are independent flags. Every lifecycle transition writes to `CardHistory`, which also backs the archived/deleted list's "when" display via `MAX(Timestamp)` — there's no dedicated timestamp column for that.
- **Settings**: in-app preferences live in the SQLite `Settings` key/value table (`GetSetting`/`SetSetting`), read once into `MainViewModel` at `Load()`. `AppConfig`'s JSON file is only for bootstrap info needed before the DB is even open.
- **`Who` legacy column**: `Cards.Who` (free text) still exists alongside `WhoId` (FK to `People`), kept only for the one-time `BackfillPeopleFromLegacyWho` migration. Don't write to `Who` in new code.
- **Recurrence**: `SpawnNextOccurrence` creates the next task when a recurring one completes — check this if adding new completion-adjacent behavior. `Cards.RecurrencesLeft` (0.111.0, file format 3) is how many times the task still happens counting itself; null means no end. Each spawn passes one fewer and 1 is the last. Whether to spawn is `CardViewModel.HasNextOccurrence` - use it rather than re-spelling the IsRecurring/pattern/NextOccurrenceSpawned test (the delete prompts use it too). Turning Recurring off clears the count (`AddCard`/`EditCard` store it only when recurring). Templates carry it as `RecurrenceCount`.
- **Completion time**: `Cards.CompletedAt` is set whenever a card enters the Done column (`DatabaseService.MoveCard`, or `AddCard` straight into Done) and cleared when it leaves (`MoveCard` to any other column, `ReactivateCard`). `UpdateCard` never touches it, so edits don't move it. Archiving keeps the card's Done column, so archived cards keep theirs. Anything that puts a card into or out of Done by another route must maintain it too. Pre-existing Done/archived cards are backfilled at startup from `CardHistory` ("Moved ... to Done" / "Added to Done"), then the archive time, then `LastUpdated`.
- **Email This Task** (`OutlookEmailHelper`): classic Outlook is driven by late-bound COM and gets attachments plus the user's signature. If COM can't open a compose window (the new Outlook has no COM, or no Outlook is installed), it falls back to a `mailto:` link in the default mail app (capped at `MaxMailtoLength`) and opens a temp folder with the task's import `.xlsx` and attachment copies to drag in. Only fall back before the Outlook window is showing, otherwise the user gets two emails.
- **Website links are restricted**: `UrlLauncher.TryNormalize` only lets http/https (with a dotted host or `localhost`, no user-info) and `mailto:` through; bare `name@x.y` becomes `mailto:`, a bare host gets `https://`. `UrlLauncher.Open` refuses anything else at launch time (a task file can come from someone else), and Add/Edit Task refuses to save it. Anything new that hands a stored string to `ShellExecute` should go through the same check.
- **Filter list heights**: the Project list and the Priority/Who pair bind `Height` to `MainViewModel.ProjectFilterListHeight` / `PriorityWhoFilterListHeight` (clamped 50–600, default 140, not rounded so fractional drag steps on scaled displays still add up). A `Thumb` under each (`FilterResizeGripStyle`, `Tag` says which) adds `DragDelta` straight on, saves to Settings on `DragCompleted`, and resets on double-click.
- **Report a Problem** (`ProblemReport`): Help and About buttons, plus a Yes/No offer in `App`'s unhandled-exception prompt. Copies the newest 512 KB of `crash.log` (next to the task file) to a temp folder and opens an email to `AppInfo.SupportEmail` through `OutlookEmailHelper.ComposeEmailWithFiles`, which has the same classic-Outlook-then-mailto fallback as task emails.
- **Due time / time alerts**: `Cards.DueTime` is an optional `"HH:mm"` string alongside the date-only `DueDate`; `CardViewModel.DueDateTime` combines them. `MainWindow` owns the app's only periodic timer (`_dueTimeTimer`, 15s), which hands `GetCardsPastDueTime()` to `TimeAlertTracker` (`ViewModels/`, unit-tested) and raises `ReminderWindow` in `isTimeAlert` mode for whatever it returns. The tracker keeps a session-only set of `(CardId, DueAt)` already announced plus snoozes keyed the same way; anything already past when the window opens is pre-seeded, so times missed while the app was closed never pop (the startup reminder list covers them). Snooze options live in `TimeAlertTracker.SnoozeOptions`.
- **Non-modal windows and `IsCancel`**: WPF's `IsCancel` only closes a window opened with `ShowDialog()`. The time alert is opened with `Show()` (so it doesn't block the board), so its Close button needs an explicit `Click` handler. Any future `Show()`-opened window needs the same.
- **Board card lists are virtualized**: each column's `ItemsControl` uses a `VirtualizingStackPanel` with the `ScrollViewer` inside its own template (pixel scrolling), so only on-screen cards are built. It binds to `ColumnViewModel.CardsView`, a live-filtered `ListCollectionView` over `Cards` that leaves out cards whose `IsVisible` is false — collapsing them instead would make the panel build every hidden card it passes. Set `IsVisible` and the list follows (live filtering applies a moment later on the dispatcher, so tests read the list after letting it run). Changing more than `BulkChangeThreshold` cards at once goes through `BeginBulkChange()` (`ApplySort`, `ApplyFilters`), which detaches the view and hands the board a fresh one at the end — never use that path while a card drag or card popup could be in flight. Drag-reorder (`CardsArea_*`, `GetCardDropTarget`) works in the list's on-screen coordinates and only looks at cards that have an element, mapping the matched one back to its index in `Cards`. Anything new that walks card containers must expect most cards to have none. Measured on a generated 6,000-task board (plus 6,000 archived): board opens in 0.75 s (was 21.9 s), 200 MB (was 1.9 GB), filters/sorts about 0.3–0.5 s (were 1.5–3 s), resize 30 ms (was 2–4 s). The panel also lays every card out at least as wide as the widest card it has ever measured (it remembers that width for cards scrolled out of view), so after a column's scrollbar appears or the column is narrowed, cards ran under the scrollbar (0.112.0). Each card's `Width` is therefore bound to the list's `ScrollViewer.ViewportWidth` (`ViewportWidthToCardWidthConverter`, left-aligned) - keep that binding if the card template changes.
- **Column width**: the board's columns are `EffectiveColumnWidth` wide. With `IsFitColumnsToWindow` (setting `FitColumnsToWindow`, on unless "False"; in the Settings snapshot) that is the board's width - reported by `BoardScrollViewer_SizeChanged` through `SetBoardWidth` - shared among the columns less the 12px `ColumnGap`, floored at `MinColumnWidth` (240 - measured: a card's six quick buttons need 147px and the column/card padding plus the list scrollbar 59px) so a narrow window scrolls sideways; off, it is the fixed `ColumnWidth`, clamped to the same minimum (on load too). The project name on a card trims with "..." rather than being cut. The button column is never resized by this - it is shown or collapsed as before, and the board takes whatever is left.
- **Settings Cancel**: every control on the Settings dialog writes through immediately, so Cancel / Esc / X work by restoring `MainViewModel.CaptureSettings()` taken when the dialog opened (`RestoreSettings`, in `MainViewModel.SettingsSnapshot.cs`), after an "unsaved changes" confirm if the snapshot differs. **A new preference added to Settings must be added to `SettingsSnapshot` too**, or Cancel will silently keep it; `SettingsCancelTests` fails if a snapshot field never changes, but can't notice a field that was never added. Actions (Back Up Now, moving/switching the task file, recent-files tidy) are deliberately outside it.
- **Excel import header row** (`ImportService.FindHeaderRow`): the first row with a title heading ("Title"/"Task"/"Task Details", any column) plus at least one other known heading; failing that, the first row with a title heading alone. Heading aliases live in the `*Headings` arrays.
- **Multi-card selection** (`MainViewModel.Selection.cs`): `CardViewModel.IsSelected` is screen-only state, set by Ctrl/Shift+click in `Card_PreviewMouseLeftButtonDown` (clicks on a card's own buttons are ignored). A card drag carries the grabbed card under the `CardViewModel` format plus, when it's part of the selection, the group under `CardGroupFormat` — always read it with `MainWindow.GetDraggedCards`. `MoveCards` / `ReorderCardsWithinColumn` do the group moves (the single-card reorder delegates to the latter). Hiding a card through filters deselects it (`SetCardVisible`), so a drag can't carry cards the user can't see.
- **UI Automation cost**: when an accessibility-type client is running (common), WPF builds automation peers for every element of every window the first time a second window opens — that was a 26 s one-time freeze on a 6,000-card unvirtualized board. Keep element counts proportional to what's on screen.
- **Card right-click menu**: `MainWindow.Card_PreviewMouseRightButtonUp` builds a fresh `ContextMenu` on every open, and each entry reuses the path its button or quick-edit already takes (`DeleteCardWithConfirm`, `MoveCardDeferred`, `SetCardPriority`, ...), deferred via `BeginInvoke` like the quick-edit menus. The app-wide `MenuItem` template in `App.xaml` replaces the stock one for dark-theme reasons, so submenus only open because that template has a `PART_Popup` bound to `IsSubmenuOpen` — keep it if the template is ever touched. `Copy as Text` uses `CardTextFormatter`, which shares due-date/goal wording with the plain-text email.
- **Right-click on a selection**: when the clicked card is part of a selection of two or more, `Card_PreviewMouseRightButtonUp` builds `BuildSelectionMenu` instead of `BuildCardMenu` (right-clicking outside the selection clears it first). Group changes go through `SetCardsPriority` / `SetCardsWho` / `SetCardsProject` (`MainViewModel.Selection.cs`), which persist each card but re-sort and refresh once via `ChangeCards` - a new bulk field change should use it too rather than looping the single-card setter. Group delete (`DeleteCardsWithConfirm`) always confirms regardless of `ConfirmDelete`, and asks the recurring keep/end-series question once for the group through `DeleteRecurringTaskWindow`'s second constructor. Names shown as menu entries go through `MenuText` so an underscore isn't eaten as an access key. `PreviewMouseRightButtonUp` is a direct event: a test harness must raise it on the card's root `Border`, not a child.
- **Undo** (`MainViewModel.Undo.cs`, `DatabaseService.Undo.cs`): works by copy, not by reversing each action. An action wraps itself in `using var undo = RecordUndo(label, cardsItWillTouch)` *before* changing anything; that copies those tasks' stored rows (`SELECT *`, so new `Cards` columns are covered automatically) plus flags and sub-tasks. `Undo()` writes the copies back in one transaction, removes any card the step created (`AddCard` registers into the open recording - erased if it has no attachments, otherwise sent to the Deleted list so its files survive), then updates the on-board `CardViewModel`s in place via `TakeValuesFrom` (a deleted/archived card's original object is kept in the step's `Removed` map and reused, so references stay valid). Recordings nest: everything inside the outermost `RecordUndo` is one step under its label, which is how group actions and a recurring task's spawned next occurrence undo together. Drag-reorder also records the column's stored order and the active sort keys. **Any new action that changes cards must call `RecordUndo` first**, and a new stored card field must be added to `CardViewModel.TakeValuesFrom` (and `BuildCardViewModel`). Deliberately outside Undo: attachments (files move/are erased on disk - undo only re-runs `ReconcileAttachmentLocations` for the restored status), managed lists, Settings, and the Archived/Deleted screens. A project/goal/person/flag deleted since the snapshot is restored as none. Session-only, 30 steps, no redo. Each undone card gets an `Undone` history row.
- **Start date / Hide Future**: `Cards.StartDate` is an optional date-only "not before" (`CardViewModel.StartDate`, `IsNotStarted`, `StartDateDisplay` - the card's "Starts ..." line only shows while it is still ahead). It may never be after the due date: the task dialog refuses it, `SetCardDueDate` pulls it back, and import clamps it (`StartNoLaterThanDue`). `SpawnNextOccurrence` keeps the same start-to-due gap. `MainViewModel.HideFutureTasks` (the Hide Future button, Settings key `HideFutureTasks`) is a view setting, not a filter: it lives in `FilterCriteria.HideNotStarted` so `Matches` applies it, but `ClearFilters`, Esc and custom filters don't touch it, and it never hides a card with a `CompletedAt`. It must be read before `Load()` in the constructor, because `Load` applies the filters. "Today" changing matters to it, to the Starts line and to overdue highlighting, so the window's 15 s timer calls `RefreshIfDayChanged`. Reports and the Timeline ignore Hide Future (they have their own filters).
- **Timeline arrows** (`Services/TimelineLayout.cs`, unit-tested; drawn by `TimelineWindow.BuildGrid` and again by `BuildPrintDocument`): a task with a start date has its box at the start (left) and an arrow running right to the middle of its due column; a task with no start date is just a box at its due date. `TimelineLayout.Place` turns a project's tasks into `TimelineItem`s (first/last column clamped to the window, a lane so nothing overlaps - arrows are placed before single boxes, `StartsBeforeWindow`, `DueAfterWindow`). A start before the left edge means there is no start column, so the box goes in the first column, dashed; a due date past the right edge just runs the arrow off the edge. On screen each project row is background cells plus a lane `Grid` laid over them (same column widths, one auto-height row per lane) so an arrow can span columns; print does the same geometry by hand on a canvas. The arrow uses `PrimaryTextBrush` on screen (black on light, white on dark) and black in print. A task is on the Timeline if its start-to-due span touches the window (`IsInWindow`), so start-only tasks appear. Any change to the layout rules goes in `TimelineLayout`, never separately in the two drawing paths. The Day/Week view is remembered in the `TimelineView` setting (saved as soon as it is switched). The window's size and maximized state are remembered in the `TimelineWindowSize` setting (`MainViewModel.TimelineWindowSize` / `SaveTimelineWindowSize`), clamped to the screen on the way back in; position is not kept, it always opens centred on the board.
- **Day filters and start dates**: Today / Tomorrow / Within a Week match on the due date *or* a start date falling on those days (`MainViewModel.StartsBetween`, shared with `ReportService`'s Due filter). Tomorrow and Within a Week also override Hide Future for the tasks they matched by start date - otherwise the two would cancel out.
- **Waiting On**: `Cards.WaitingOn` is free text (who or what is holding the task up); non-blank means waiting (`CardViewModel.IsWaiting`, `WaitingOnDisplay`; the setter trims and turns blank into null). Set from the task dialog, by clicking the card's highlighted line, or from the right-click menus, the last two through `MainWindow.PromptWaitingOn` (`PromptWindow` with an initial value - saving it empty clears). `MoveCard` clears it on the way into Done; a spawned recurring occurrence doesn't inherit it; Duplicate does. Moving into the column *named* "Waiting" prompts once for the moved cards that don't already say (`MaybePromptWaitingOn`, called beside `MaybePromptCompletionNote`). **The Waiting On button is a `DueFilter` value** (`MainViewModel.WaitingOnFilter`), not a filter of its own: it shares the Today/Tomorrow button row and behaviour, and riding on `DueFilter` gets it remembered between sessions, saved in custom filters and reset by Clear Filters for free. It is the one `DueFilter` value that isn't about a date - `ReportService` ignores it. Keyword search covers it. New stored card fields like this one need: schema `MigrateColumn`, `CardItem`, `GetCards` (mind the reader indexes - `ArchivedAt` is last), `AddCard`/`UpdateCard`, `CardViewModel` + `TakeValuesFrom`, `MainViewModel.AddCard`/`EditCard`/`PersistCard`/`DuplicateCard`, the dialog (including its unsaved-changes snapshot), and the text/Excel outputs.
- **Waiting On suggestions** (`MainViewModel.WaitingOnHistory.cs`, `Views/TextBoxSuggestions.cs`): a task's Waiting On is cleared when it is finished, so past answers are kept separately in the `WaitingOnHistory` setting (JSON list, newest first, 50 at most, one per answer whatever its capitals). Every path that sets a value calls `RememberWaitingOn` (`AddCard`, `EditCard`, `SetCardWaitingOn`, `SetCardsWaitingOn`); `WaitingOnSuggestions` is that list followed by anything on a task now that was never typed. `TextBoxSuggestions.Attach(box, suggestions, forget, openWhenEmpty)` is a reusable helper, not tied to Waiting On: a non-focusable list in a Popup under the box plus inline completion of the first starts-with match, with the added part selected. **Enter is deliberately not handled**, so the window's default button saves whatever is in the box; Esc closes the list before it reaches the window. It completes only when characters are added at the end (never while deleting), and keeps what the user really typed in `_userTyped` so a guess that is turned down gives back their own capitals. `openWhenEmpty` is on for the one-question `PromptWindow` and off for the task screen, where a list popping up while tabbing through the form would be noise. The matching rules (`Matches`, `Completion`) are static and unit-tested; the typing behaviour was checked in a real window with `TextCompositionManager`.
- **Managing the Waiting On list** (`ManageWaitingOnWindow`, second half of `MainViewModel.WaitingOnHistory.cs`): `WaitingOnEntries` is the suggestions alphabetically with how many board tasks say each; `AddWaitingOnSuggestion`; `RenameWaitingOnSuggestion` rewords the list entry in place **and every board task that says it** (through `ChangeCards`, so one Undo step for the tasks; renaming onto an existing answer merges them); `DeleteWaitingOnSuggestion(text, clearFromTasks)`. The list itself is outside Undo like every managed list; the tasks are inside it. An answer a task still says can't really leave the suggestions, which is why Delete asks. Reached from the prompt's "Manage list..." link (`PromptWindow`'s `manageSuggestions` callback, which also refreshes the open prompt's suggestions via `TextBoxSuggestions.Replace`), the task screen's List... button (which follows a rename of the task being edited, so saving doesn't put the old wording back), the Waiting On button's right-click menu, and the card and selection Waiting On submenus.
- **Task file version stamp** (`DatabaseService.FileStamp.cs`): the `FileFormat` setting holds the newest file format that has ever saved the file, `FileFormatAppVersion` the app version that raised it, `LastOpenedByVersion` whoever opened it last. `DatabaseService.CurrentFileFormat` is **not** the app version: it goes up by one only when what is stored changes shape (a new table or column, or a new meaning for an old one), so the warning isn't shown for ordinary releases. The stamp only ever goes up. On startup `App` checks `db.IsFromNewerApp` and shows a Yes/No warning (default No = close) before any window opens. `FileFormatTests.ChangingTheTables_MeansRaisingTheFileFormat` fingerprints every table and column and fails when they change without the number changing - **when it fails, raise `CurrentFileFormat` and paste the new fingerprint from the failure message**. Add that step to the stored-card-field checklist under Waiting On. Copies of the app from before 0.102.0 know nothing of the stamp and cannot warn.
- **Update check** (`Services/UpdateChecker.cs`, `MainViewModel.Updates.cs`, `MainWindow.Updates.cs`, `UpdateAvailableWindow`): at most once a day at startup (`IsUpdateCheckDue`), in the background, it asks the GitHub releases API for the latest release of the **public** downloads repo - the same release the download page reads, so publishing a release is all it takes to notify installed copies. A newer, non-skipped version opens the notice once no other window is up (`ShowUpdateWhenQuiet`); its notes are the release body's `- ` bullets, i.e. that version's CHANGELOG bullets. Get the Update opens `AppInfo.DownloadPageUrl` - **never a link taken from the reply**; nothing from the reply is trusted beyond being shown as text, and the app never downloads or runs anything. Failure of any kind is silent. Settings: `CheckForUpdates` (in the Settings snapshot), `LastUpdateCheck:<computer>`, `SkippedUpdateVersion`. About > Check for Updates ignores the skip, always answers, and deliberately does **not** record a check (so trying it never postpones the automatic one). **Per-PC state in a shared task file:** the user runs two PCs against one task file, and the first version stored the last-check time under one shared key, so whichever PC started first each day silenced the other. Anything that belongs to the PC rather than to the tasks is now stored under a key carrying `MainViewModel.ThisComputer` (the machine name; settable for tests): the last update check and `LastSeenVersion:<computer>` for What's New (which falls back to the old shared `LastSeenVersion` when this PC has none, so a single-PC user upgrading is not shown it twice). It stays in the task file rather than `AppConfig` so tests and self-checks never touch anything outside their own folder. Apply the same rule to any future per-PC state; window sizes, theme and the collapsed button column are still shared, deliberately, as preferences. `UpdateChecker.FetchOverride` stands in for the internet in self-checks; no unit test makes a request. **This is the only time the app contacts the internet by itself. `Legal/PRIVACY.txt` describes it exactly (what is sent, to whom, how to turn it off) - any change here, or any new network use at all, must update the Privacy Note in the same commit.**
- **Legal documents** (`Legal/EULA.txt`, `Legal/PRIVACY.txt`): embedded in the exe (`LegalDocuments`), shown from About via `LegalWindow`, and EULA.txt is also the installer's `LicenseFile`. Decisions the user made: one licence = one person on any PCs they use; governed by Ontario law; support address is `AppInfo.SupportEmail` (currently the Gmail address). The documents spell out the company name and support address in their text, so changing either in `AppInfo` means editing both files too - `LegalDocumentTests` fails until they match. They were drafted without a lawyer; the user has been told to have them reviewed before selling.
- **Shared tasks (several people on one task)**: the `CardPeople` join table (`DatabaseService.CardPeople.cs`) holds a task's people in picked order; **the first is the lead and `Cards.WhoId` is always kept equal to it** (`SetCardPeople` -> `SyncLead`; `DeletePerson` promotes the next person). Older single-person paths and older copies of the app therefore still read one person from the card row; a row whose `WhoId` disagrees with the list (an older app edited it) is read as just that person. `CardViewModel.People` is the only setter - `WhoId`, `LeadName`, `WhoEmail` (lead), `WhoName` (everyone joined, for display), `PeopleEmails`, `CanEmailCard` all derive from it, and `RefreshPeople()` re-raises them after a rename/email change (cards hold the live `PersonViewModel`s). `AddCard` takes an optional `people:` (else `[who]`); `EditCard` takes the list and nothing else. `PersistCard` does **not** write people - callers that change them also call `PersistPeople` (`SetCardPeople`, `ToggleCardPerson`, `SetCardsWho`, `AddPersonToCards`, `RemovePersonFromCards`). Rules the user chose: Who filter = any of the task's people; Sort by Who = lead; email = everyone with an address (`OutlookEmailHelper.JoinRecipients`, "; " for Outlook, commas inside `BuildMailtoUri`); report Group by Who = under each person with "(shared - also listed under ...)" via `BuildMetaParts(row, whoGroup)`, row count still one per task; Excel = names separated by semicolons (`MainViewModel.SplitPeopleNames`; commas stay inside a name). Undo snapshots `CardPeople` too. Templates store `PeopleIds` plus `WhoId` (`AllPeopleIds` reads old ones). The Imported Tasks screen still edits one person per row - the lead - and keeps the others. The dialog's picker is `AddTaskWindow.People.cs` (a ToggleButton + Popup of tickboxes; `_selectedPeople` order is the lead order).
- **Panel colours**: theme brushes set in `ThemeManager.Apply` (defaults in `App.xaml`). `AccentPanelBrush`/`AccentPanelBorderBrush` are the header bar: mid-blue in light, deep navy in dark, and **white text sits directly on it, so keep it at 4.5:1 or better against white**. `SidebarPanelBrush`/`SidebarPanelBorderBrush` are the button column: pale blue in light mode (the user found a mid-navy washed the slate and blue buttons out), deep navy in dark. Nothing in the button column is drawn straight onto that background except separators and the resize grips (`SidebarGripBrush`) - every label and button is its own coloured box with white text - so a new element placed directly on it needs a colour that works on both the pale and the navy.
- **Collapsible button column** (`MainViewModel.Sidebar.cs`): `IsSidebarCollapsed` swaps the 344-wide column for a 30-wide strip docked on the same side (both are in `MainWindow.xaml`, one always collapsed). Because the filters are out of sight while collapsed, the strip shows `HiddenTasksLabel` ("3 hidden by filters"): `HiddenTaskCount` is simply every card with `IsVisible` false, whatever hid it, and is refreshed at the end of `ApplyFilters` and in `RefreshDashboardStats`. - **Compact buttons** (second half of `MainViewModel.Sidebar.cs`; Settings, so it **is** in the Settings snapshot): a tighter button column, 300 wide instead of 344 and about 140 shorter. **Tighter, not smaller text** - some labels are 9 px already, so plain scaling was rejected. - **Quick Report and relative report dates** (`Services/ReportRunner.cs`, `Services/RelativeDate.cs`, `QuickReportWindow`): `ReportRunner` runs a `SavedReportView` straight from its stored fields (rows, FixedDocument, PDF, and the parameter summary), so a report can be made without the Report Builder screen; the Report Builder still builds from its own controls, and the two agree because both call `ReportService.BuildRows`. A saved view's `DueFrom`/`DueTo`/`ArchivedFrom`/`ArchivedTo` can be a fixed `yyyy-MM-dd` or a relative `today`, `today+7`, `today-30` (`RelativeDate.Resolve(saved, today)`, resolved on the day the report runs). In the Report Builder a picker shows the real day and carries the relative text in its `Tag` for as long as it still shows that day (`SetDate`/`SavedDate`): re-saving a loaded view keeps it relative, picking a day by hand makes it fixed. The Today buttons save `today`; right-click offers `today±N`. `DateKindText` under the pickers says which kind each date is (`RefreshDateKind`, on every change), because the pickers themselves always show a real day and the user could not tell the two apart. `SetDate` is an instance method for that reason. - **Task templates** (`Models/TaskTemplate.cs`, `DatabaseService.Templates.cs`, `MainViewModel.Templates.cs`, `AddTaskWindow.Templates.cs`, `ManageTemplatesWindow`): a `TaskTemplates` table holding `Id`, `Name` and the rest as one JSON value, so adding a task field to templates needs no schema change - add it to `TaskTemplate`, `TemplateFromCard`, `AddTaskWindow.BuildTemplateFromForm` and `ApplyTemplate`. - **Quick Add** (`MainWindow.QuickAdd.cs`, `QuickAddWindow`, `MainViewModel.QuickAdd.cs`, `Services/QuickAddParser.cs` - the parser is pure and unit-tested): `RegisterHotKey` on the main window's handle (Ctrl+Alt+N; the Test build adds Shift so both can run together), delivered as `WM_HOTKEY` to a hook added in `OnSourceInitialized`. It only works while the app runs. If Windows refuses the key, `MainViewModel.QuickAddHotkeyProblem` is set and Settings shows it. One Quick Add window at a time; it is topmost, does not close on losing focus, and stays open after each add. `QuickAddHotkeyEnabled` is a Settings preference, so it is in `SettingsSnapshot`. Parser rule: a code is only a code when the whole word matches (`!high`, `@start-of-one-person's-name`, `/tomorrow` `/fri` `/+3` `/10-15` `/2026-10-15`); anything else stays in the title untouched. `MainWindow.ShowStatusMessage` is the shared "line at the foot of the board" used by Undo and Quick Add.
- **Testing windows outside the app**: to render real windows from a scratch exe, reference `KanbanApp.csproj`, set `Application._resourceAssembly` (private static, via reflection) to the KanbanApp assembly, create a plain `new Application()`, and give it App.xaml's resources by `XamlReader.Parse`-ing the inside of `<Application.Resources>` wrapped in a `<ResourceDictionary>`. For multi-window UI checks, drive the steps from inside a real `Application.Run()` loop with `await Task.Delay(...)`.

## Known rough edges

- **Dashboard colours** (`DashboardPalette` in `Views/DashboardCharts.cs`) were checked with a palette validator (colour-blind separation of neighbouring colours, contrast against the chart card) separately for light and dark - dark is its own set of steps, chosen by `MainViewModel.IsDarkMode`, not a flip. On Hold is magenta, not the board's orange: orange beside In Progress yellow failed the check. Re-check any colour change the same way rather than by eye. Text never takes a series colour; single-series charts use one blue; projects and people are horizontal bars sharing one scale; more than 20 projects fold into "Other". Completions per week and "Done in 7 Days" include archived tasks (`GetArchivedCompletionDates`) and weeks start on the PC's first day of the week.
- No DB migration versioning — fine at current scale, but there's no rollback story if a migration ever needs undoing.
